### Inspect the actual schema before migration

The existing server insert was inspected, but the live table definition was not.
This operator-run query prints schema metadata only. Review that this loads the
same connection configuration as the actual server; **stop** if the server uses
a different connection mechanism or search path. Do not print connection values.

```bash
cd "$API"
node <<'NODE'
const { Pool } = require('pg');
require('dotenv').config({ path: '.env', quiet: true });
const pool = new Pool(process.env.DATABASE_URL
  ? { connectionString: process.env.DATABASE_URL } : undefined);
(async () => {
  const client = await pool.connect();
  try {
    await client.query('BEGIN READ ONLY');
    const r = await client.query(`
      SELECT table_schema, table_name, column_name, data_type,
             is_nullable, column_default
      FROM information_schema.columns
      WHERE table_name IN ('events','invites')
      ORDER BY table_schema,table_name,ordinal_position`);
    console.table(r.rows);
    const constraints = await client.query(`
      SELECT n.nspname AS schema_name, c.relname AS table_name,
             con.conname, pg_get_constraintdef(con.oid) AS definition
      FROM pg_constraint con JOIN pg_class c ON c.oid=con.conrelid
      JOIN pg_namespace n ON n.oid=c.relnamespace
      WHERE c.relname IN ('events','invites')`);
    console.table(constraints.rows);
    await client.query('ROLLBACK');
  } finally { client.release(); await pool.end(); }
})().catch(error => { console.error(error.message); process.exitCode=1; });
NODE
```

**Stop for review** unless `events.id` generation/defaults, all required columns,
owner fields, date storage, and `invites.event_id`/token/expiry match the new
router's SQL. In particular verify timestamp semantics: new instants are UTC ISO
strings; no historical rows may be reinterpreted or rewritten. If `time_zone`
already exists, verify it is nullable text with compatible meaning. Resolve
multiple schemas/search paths explicitly, rather than altering an arbitrary table.

## 5. Smoke checklist

Use a designated test owner, second test account, and synthetic event. Do not
send email to real guests or change/delete existing customer events for testing.

- [ ] Signed-out event list/detail access rejects authentication. Second owner
  cannot list, read or update the first owner's event.
- [ ] Create a New York event for **July 4, 2027, noon** while the browser/device
  is in a different timezone. Stored start is **2027-07-04T16:00:00.000Z** with
  `time_zone=America/New_York`; displayed time is **12:00 PM EDT**.
- [ ] Verify owner list/detail, invitation, active `/rsvp.html`, keepsake, and
  shared mobile display. Check email content only with an authorized test mailbox.
- [ ] Valid live guest token works without owner email/UID in its detail response.
  Expired, invalid, and another event's token fail.

  (fold) fail with clear guidance and create no event. Choose 03:30/02:30,
  respectively, to confirm retry with a valid time works.
- [ ] A preexisting event with null timezone retains its stored instant and
  previous presentation. Its owner list, invitation and RSVP still work.
- [ ] Weather/current location, landmark and city search, historical plans,
  invitation creation, RSVP persistence and existing notifications still work.
- [ ] Header, favicon, social preview and shared mobile logo use the canonical

## 6. Rollback without data loss

1. Stop rollout if any critical smoke check fails. Do not repeatedly create test
   events to work around a server error.
2. Restore the prior known-good frontend release with the identified frontend
   process's established procedure. Preserve the new build for diagnosis.
3. Prefer retaining the backward-compatible timezone backend while diagnosing.
   If it must be rolled back, restore the backed-up `server.js` and original
   module files (respecting originally absent files) and restart only the API.
   Never overwrite unrelated notification fixes from a stale server copy.
4. **Keep `events.time_zone` and all values. Do not `DROP COLUMN`, delete events,
   rewrite UTC instants, or restore an old database over newly created data.**
   A full database restore requires a separate recovery decision and safeguards
   for all data written since the backup.
5. If zoned events were created before rollback, the old frontend may display
   them in the viewer's timezone. Flag that limitation, pause further event
   creation through the established operational process if necessary, and prefer
   a forward fix. Do not declare rollback behavior fully equivalent for these
   new events.
